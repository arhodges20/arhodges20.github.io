Detection-as-Code: shipping detections like software.

I built an end-to-end pipeline in my homelab where every detection rule is versioned, reviewed, tested, deployed to staging, proven with a real attack, and only then promoted to production.

Why it matters

In most SIEMs, a rule change is a live edit in a GUI. There's no review, no tests and no history. Over time, what's actually running drifts away from what the team thinks is running.

I wanted my detections handled the way good software is: written in files, reviewed before they merge, tested automatically, and shipped through a pipeline that refuses to go further when something is wrong.

The workflow

Step 1

Write the rule

Each detection starts as a TOML rule file with its ATT&CK mapping, known false positives and an investigation guide.

Alongside it I commit recorded test data (a real attack sample and a benign look-alike) and a short Alerting & Detection Strategy (ADS) doc.

Step 2

Three CI checks on every pull request

These run on GitHub-hosted runners:

  • Rule validation: schema, query syntax, ECS field names and ATT&CK IDs, plus a strict build using the same loader as the deploy.
  • House standards: my own pytest tests.
  • Replay: a throwaway Elasticsearch loads the recorded data. The rule must fire on the attack and stay silent on the benign data.

Step 3

Review and merge

Every pull request has a checklist covering field behavior, false positives, triage context and severity.

The main branch is protected, so merging is blocked until the checks pass. Changes land as squash merges.

Step 4

Deploy to staging

Merging triggers a deploy from a self-hosted runner inside the lab. The runner only makes outbound connections.

It deploys into a separate Kibana staging space using a least-privilege service account.

Step 5

Attack and verify

For each changed rule with a mapped test, the pipeline runs the matching Atomic Red Team test on a dedicated Windows target, then waits for that rule's alert in staging.

No alert means the deploy stops.

Step 6

Promote to production

Rules reach production only if staging succeeded. They update in place by rule ID.

After it ships

Drift detection

A nightly job compares Kibana with git, looking for GUI edits and for disabled, missing or untracked rules. Anything that differs becomes a GitHub issue.

Design decisions

  • CI runs on GitHub's runners. Unreviewed code from a pull request never runs near lab credentials. The lab runner only gets involved after a reviewed merge.
  • A separate staging space. Test alerts from attack verification stay apart from real ones.
  • A least-privilege deploy identity. The deploy uses a service account that has only the access it needs.
  • Standards enforced as code. My house standards are pytest tests, so they're checked on every pull request instead of being remembered.
  • Every rule has an ADS doc. The reasoning behind a detection ships with the detection.

What it caught while I built it

House standards

6 of 7 imported rules failed my standards

They were missing an ATT&CK mapping or false-positive guidance. All six were fixed before anything shipped.

Staging gate

1 deploy stopped at staging

A scheduling error that Kibana would have rejected stopped the deploy at staging. Production never changed. I then added a CI build step, so that class of error now fails the pull request instead.

ES|QL

3 ES|QL rules brought up to standard

Instead of permanently bypassing the check, I brought them up to Elastic's alert-field (KEEP) standard.
